# 跨部門合作設計草案 — 2026-09-13

本設計取代已停止的 Cross-department delegation 提案。現有程式 HEAD 為 `4032f55`；先前 Prompt 修正已 push，但尚未部署。這份文件是設計，尚未實作新流程。

## 使用規則

| 發起者 | 動作 | 接案者 | 預期驗收人 |
|---|---|---|---|
| Boss | 正常部門分派 | 對方部門主管；沒有主管時，該部門職位 Rank 數字最小的成員 | 原有工作流的審查與完成門檻 |
| 部門主管 | 跨部門合作申請 | 對方部門主管 | 提出申請的本部門主管 |
| Staff | 跨部門合作申請 | 對方部門主管 | 本部門主管＋提出申請的 Staff；保留既有人選不足時降為單人的規則 |

審查人選齊全時，兩人都要對同一版本通過；人選不足時維持既有單人降級機制，記錄預期人選、實際人選及原因。沒有任何合格審查者時不得視為通過。單純忙碌屬排程等待，不把未完成的審查當成批准。

移除 Positions 的 Cross-department delegation 開關、對應公開 API 設定與 Prompt 權限說明。舊資料欄位的值不再授予任何權限；採相容的 schema 遷移，避免混合版本部署時破壞既有資料。一般部門內分派維持原有規則。

Boss 的無主管備援是接案選擇，不會自動修改職位、Rank、回報線或任命正式部門主管。Rank 0 最高，數字較小優先。排除不屬該部門、停用／刪除 Agent 及失效職位；同 Rank 以固定 Agent ID 排序。主管只是忙碌或暫時無法連線時，使用等待／恢復流程，不視為「沒有主管」而越過他。空部門不能憑空分派。

無主管備援僅限 Boss 一般分派。合作接案者必須是目標部門的正式主管；找不到時把原因交給負責主管或 Boss 處理，不自行用 Rank 9 替代接案主管。來源部門主管是優先審查者，缺少合格人選時按上述降級規則處理；本輪不新增建卡前的主管核准。

## 成果如何返回

1. 記錄申請的原卡、原執行上下文、提出者、來源與目標部門、主管及預期 Reviewer。
2. 合作子卡的 `parentCardId` 必須等於提出申請的 Staff／Department Head 當下執行的申請卡 ID。assignee 為對方主管；不另掛到來源主管的其他卡、對方主管的卡或專案根卡。原卡負責人保持不變。
3. 對方主管按自己部門的正常流程處理：有員工就分派；單人主管可執行。這不會讓提出申請的 Staff 變成對方主管的上司。
4. 子卡成果送回指定審查者。本部門主管負責品質及部門責任；提出申請的 Staff 驗證成果是否滿足原任務需要。
5. 實際審查輪次中任一 Reviewer 要求修正，子卡退回對方主管；該輪所有 Reviewer 對目前成果通過，且既有證據／合併門檻滿足，才接受子卡。合格人選不足的單人審查須有降級紀錄，不能把另一人的未回覆或否決直接忽略。
6. 接受事件帶成果指標回到原卡，喚醒原卡負責人繼續整合。現階段同卡委派／Message Board 執行上下文不能直接建立合作子卡；系統須回傳可操作的錯誤，要求回到原卡負責人的 dispatch 上下文後重試，不能宣稱已支援或靜默改由其他人提出。

回流依據是固定的原卡與申請者紀錄，不依賴 Rank，也不改變組織管理關係。子卡完成不等於原卡直接 Done；原卡仍需交付自己的成果。

## 申請入口

沿用唯一 `request` 回報入口，新增明確的 collaboration 種類，讓 Agent 提供目標部門、工作範圍與驗收條件。平台根據實際組織解析主管與 Reviewer，Agent 不得自行指定其他審查者、來源人或權限。

### 已採用的流程

使用者已要求實裝並沿用現有架構。本輪不新增前置主管核准：有效申請直接在原申請卡下建立合作子卡，完成後走指定 Reviewer 優先的現有審查流程。人選不足可記錄原因後降級，忙碌則等待。

## 必須補強的現有程式

- `company-workflow.ts`：Boss 部門接案者解析、無主管備援，以及 readiness 檢查；備援不能被現有「一定要有主管」檢查再次擋下。
- `packages/shared/src/index.ts`、`agent-results.ts` 與實際回報接收路徑：統一解析 collaboration 申請與精準格式修復，不讓它落入一般求助而丟失合作資料。
- 新的合作模組：持久申請來源、在原申請卡下冪等建立子卡、配置預期 Reviewer、回流事件；不要把合作權限加入一般的 `targetsFor` 下屬清單。
- `review-rounds.ts`、`review-panel.ts` 與完成／合併證據門檻：沿用現有審查及人選不足降級規則，優先配置來源主管＋Staff；讓原卡看得到實際審查者與降級原因，而非一律宣稱完成雙人審查。
- 既有 parent rollup、delivery acceptance、recovery 與訊息委派接續：只在有效接受後回流，保留原卡擁有者與執行上下文。
- Positions UI、API Help、角色／操作 Prompt：刪除舊開關，明確區分「部門內分派」及「跨部門合作申請」。Kanban 顯示來源、接案主管、兩個 Reviewer 各自狀態及返回原卡連結。

## 可靠性與驗收

- 相同申請、回呼或重試只建立一張合作子卡、只喚醒原上下文一次；服務重啟後仍能續接。
- 禁止跨公司、自身部門偽裝成跨部門、偽造提出者／Reviewer、重複循環申請；沿用共同深度、並行數、重試和成本上限。
- Reviewer 忙碌可等待；停用、runtime 不可用、失去資格或角色變更造成不足時，按既有規則降為單人並記錄原因。已進行中的審查不能無紀錄地移除人選或抹掉否決；無合格人選仍交恢復流程處理。
- 成果 revision 改變會使舊審查失效；不能把舊版的一次通過與新版的另一次通過拼成雙重批准。
- 覆蓋 Boss 無 Head／Rank 並列／空部門、Head 發起、Staff 發起、雙人一批一退、合法單人降級／零人不能通過、審查中成果變更、重複回呼、重啟、子卡再分派、來源為同卡委派及回到原執行者。特別斷言核准者和接案者都不能改變合作子卡的原卡歸屬。
- 確認前次 Prompt 修正的完整 API URL、公司名冊／CV、對話最尾等行為仍然通過。
